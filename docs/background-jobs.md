# Фоновые задачи

Единая конечная команда (рабочая директория `backend`):

```sh
python manage.py run_background_jobs
```

Она последовательно выполняет `expire_reservations`, `close_periods`, `notify_overdue`,
`generate_weekly_reports` и завершает процесс. Не запускает сервер, бесконечный worker
или локальную базу. Использует те же настройки PostgreSQL и секреты Django, что и web-сервис.
Для закрытия периодов и отчетов нужен хотя бы один активный admin или accountant.
Без него запуск завершается ошибкой до изменений.

В текущей архитектуре Vercel + Supabase команда запускается синхронно через
`POST /api/internal/jobs`. Создайте отдельный криптографически случайный секрет
(минимум 32 символа, рекомендуется 32 случайных байта в hex) и сохраните одинаковое
значение в переменной Vercel `CLOUD_JOB_SECRET` и Supabase Vault под именем
`bakery_job_secret`. В Vault также сохраните `bakery_job_url` — полный HTTPS URL
production-домена с путем `/api/internal/jobs`. Не используйте service-role ключ
Supabase как секрет cron и не добавляйте секрет в исходники или SQL расписания.

В Supabase включите Cron (`pg_cron`) и `pg_net`. После создания секретов в Vault
выполните в SQL editor от административной роли:

```sql
select cron.schedule(
  'bakery-background-jobs',
  '*/5 * * * *',
  $job$
    select net.http_post(
      url := (select decrypted_secret from vault.decrypted_secrets where name = 'bakery_job_url'),
      headers := jsonb_build_object(
        'Content-Type', 'application/json',
        'Authorization', 'Bearer ' || (select decrypted_secret from vault.decrypted_secrets where name = 'bakery_job_secret')
      ),
      body := '{}'::jsonb,
      timeout_milliseconds := 60000
    );
  $job$
);
```

Это инструкция для настройки, а не выполненная миграция. При повторной настройке
обновите существующее задание с этим именем. Расписание проверяет задачи каждые пять
минут; резерв снимается ближайшим успешным запуском, не в точную секунду истечения.
HTTP timeout выше рассчитан на завершение пачки за минуту. Согласуйте его с реально
настроенной длительностью Vercel Function и измеренным временем пачки.
`pg_net` отправляет HTTP асинхронно: успех SQL cron означает постановку запроса,
а не успешное выполнение задач. Проверяйте HTTP status и ошибки в `net._http_response`,
а также Cron run history. [Документация pg_net](https://github.com/supabase/pg_net).

HTTP endpoint принимает только POST (GET → 405), проверяет Bearer через constant-time
comparison (неверный/отсутствующий → 403), при отсутствующем/коротком секрете возвращает
503. Успех либо занятая блокировка → 200 `{"status":"ok"}`; ошибка задачи → 503
`{"status":"unavailable"}`. Ответы не раскрывают вывод команд/исключения и имеют
`Cache-Control: no-store`. CSRF exemption касается только этого endpoint; браузерные
операции продолжают требовать CSRF. Доступ к Vault и таблицам очереди pg_net должен
оставаться административным: расшифрованный Bearer попадает в headers очереди.
[Примечание Supabase о доступе к заголовкам](https://supabase.com/docs/guides/troubleshooting/database-roles-can-read-request-headers-queued-by-pg_net-ad6357).

Не используйте `start-worker.ps1` в облаке: это локальный цикл с localhost PostgreSQL
и локальным скриптом резервного копирования. Бэкапы облачной БД настраиваются отдельно
на стороне провайдера; эта команда их не создает.

## Повторные и конкурентные запуски

- PostgreSQL: `pg_try_advisory_xact_lock` с общим фиксированным ключом защищает всю пачку.
  Второй экземпляр команды сразу пишет `status=skipped reason=already_running` и выходит успешно.
  Транзакционная блокировка совместима с transaction pooling: она освобождается при
  commit/rollback, включая обрыв соединения. Отдельного session unlock не требуется.
- Все четыре задачи находятся в одной транзакции. Ошибка любой задачи откатывает всю
  пачку и дает ненулевой exit code. Следующий запуск повторяет обработку.
  Строки `status=executed pending_commit=true` еще не означают сохранение;
  успешный commit обозначает итоговая строка `status=completed`.
- Резервы снимаются только у submitted-заказов; уже отмененный заказ пропускается.
  Закрытый период сохраняет исходный snapshot, уведомления дедуплицируются по
  получателю/клиенту/бизнес-дню, недельные архивы — по началу недели.
- Отчеты используют тот же `report` расчет, что API. Автоматический режим догоняет
  завершенные недели с первой записи реестра; ручной `--start` у отдельной команды
  может заморозить незавершенную неделю и не используется cron.
- Уведомления записываются в БД и видны после commit. Отправка SMS/email здесь не реализована.
  Бизнес-дни и недели рассчитываются в `Asia/Almaty`, независимо от UTC расписания cron.

## Эксплуатационные ограничения

Общая транзакция удерживает блокировки до окончания отчетов. Большой исторический
catch-up увеличивает задержку освобождения резервов; сбой отчета откатывает и снятие
резервов. Для большого объема данных потребуется отдельная сохраняемая lease-блокировка
или выделенное прямое PostgreSQL-соединение и отдельные транзакции задач.
При CLI запуске отслеживайте ненулевые exit codes и отсутствие `status=completed`.
При HTTP запуске вывод команд скрыт; отслеживайте HTTP 503/504/сетевые timeout и
общую запись `Scheduled background jobs failed` в логах Vercel.
Advisory lock предотвращает наложение пачек, но не ограничивает их длительность.
HTTP timeout сам по себе не гарантирует немедленную остановку обработки сервером.
Лимит длительности Vercel зависит от плана, runtime и настройки deployment;
проверьте фактический лимит перед включением расписания. Превышение может дать 504.
[Настройка длительности Vercel](https://vercel.com/docs/functions/configuring-functions/duration).
Долгую историческую генерацию нельзя бесконечно повторять в короткой функции:
потребуется ограничение объема пачки либо отдельный механизм выполнения до включения
такого объема данных. Текущий HTTP adapter не добавляет очередь или background thread.

Блокировка координирует только экземпляры `run_background_jobs`. Не запускайте
параллельно отдельные команды через старый worker. SQLite разрешен для изолированных
тестов, общей блокировки между SQLite-процессами команда не предоставляет.
Не публикуйте Bearer-секрет клиентскому frontend.

## Проверки

```powershell
$env:DB_ENGINE = 'sqlite'
.\backend\.venv\Scripts\python.exe backend/manage.py test shop.test_background_jobs shop.test_overdue_notifications shop.test_weekly_generation shop.test_period_config shop.tests
```

Тесты новой команды проверяют реальные изменения в БД, повторный запуск,
неизменяемость snapshot, отсутствие повторных уведомлений, откат пачки при ошибке
отчета, отказ без активного сотрудника и ветку занятой блокировки.
SQLite не подтверждает реальную конкуренцию PostgreSQL; ее необходимо отдельно
проверить на тестовой PostgreSQL БД перед эксплуатацией.
