# Фоновые задачи

Единая конечная команда для Railway Cron (рабочая директория `backend`):

```sh
python manage.py run_background_jobs
```

Она последовательно выполняет `expire_reservations`, `close_periods`, `notify_overdue`,
`generate_weekly_reports` и завершает процесс. Не запускает сервер, бесконечный worker
или локальную базу. Использует те же настройки PostgreSQL и секреты Django, что и web-сервис.
Для закрытия периодов и отчетов нужен хотя бы один активный admin или accountant.
Без него запуск завершается ошибкой до изменений.

Настройте отдельный cron-сервис из того же образа/репозитория и эту start command.
Расписание `*/5 * * * *` дает проверку каждые пять минут; истекший резерв будет освобожден
на ближайшем успешном запуске, а не обязательно в точную секунду истечения.
Расписание задается средствами Railway, команда не содержит собственного таймера.
Не используйте `start-worker.ps1` в облаке: это локальный цикл с localhost PostgreSQL
и локальным скриптом резервного копирования. Бэкапы облачной БД настраиваются отдельно
на стороне провайдера; эта команда их не создает.

## Повторные и конкурентные запуски

- PostgreSQL: `pg_try_advisory_xact_lock` с общим фиксированным ключом защищает всю пачку.
  Второй экземпляр команды сразу пишет `status=skipped reason=already_running` и выходит успешно.
  Транзакционная блокировка совместима с transaction pooling: она освобождается при
  commit/rollback, включая обрыв соединения. Отдельного session unlock не требуется.
- Все четыре задачи находятся в одной транзакции. Ошибка любой задачи откатывает всю
  пачку и дает ненулевой exit code. Следующий запуск повторяет обработку.
  Строки `status=executed pending_commit=true` еще не означают сохранение;
  успешный commit обозначает итоговая строка `status=completed`.
- Резервы снимаются только у submitted-заказов; уже отмененный заказ пропускается.
  Закрытый период сохраняет исходный snapshot, уведомления дедуплицируются по
  получателю/клиенту/бизнес-дню, недельные архивы — по началу недели.
- Отчеты используют тот же `report` расчет, что API. Автоматический режим догоняет
  завершенные недели с первой записи реестра; ручной `--start` у отдельной команды
  может заморозить незавершенную неделю и не используется cron.
- Уведомления записываются в БД и видны после commit. Отправка SMS/email здесь не реализована.
  Бизнес-дни и недели рассчитываются в `Asia/Almaty`, независимо от UTC расписания cron.

## Эксплуатационные ограничения

Общая транзакция удерживает блокировки до окончания отчетов. Большой исторический
catch-up увеличивает задержку освобождения резервов; сбой отчета откатывает и снятие
резервов. Для большого объема данных потребуется отдельная сохраняемая lease-блокировка
или выделенное прямое PostgreSQL-соединение и отдельные транзакции задач.
Нужно отслеживать ненулевые exit codes и отсутствие `status=completed`; сообщения ошибок
не включают исходные сообщения провайдера/БД с потенциальными секретами.

Блокировка координирует только экземпляры `run_background_jobs`. Не запускайте
параллельно отдельные команды через старый worker. SQLite разрешен для изолированных
тестов, общей блокировки между SQLite-процессами команда не предоставляет.
Публичный HTTP trigger для cron не нужен.

## Проверки

```powershell
$env:DB_ENGINE = 'sqlite'
.\backend\.venv\Scripts\python.exe backend/manage.py test shop.test_background_jobs shop.test_overdue_notifications shop.test_weekly_generation shop.test_period_config shop.tests
```

Тесты новой команды проверяют реальные изменения в БД, повторный запуск,
неизменяемость snapshot, отсутствие повторных уведомлений, откат пачки при ошибке
отчета, отказ без активного сотрудника и ветку занятой блокировки.
SQLite не подтверждает реальную конкуренцию PostgreSQL; ее необходимо отдельно
проверить на тестовой PostgreSQL БД перед эксплуатацией.
