# Аудит действий ролей — 18 октября 2026

Проверка backend API по `docs/mvp-contract.md`. Локальные HTTP-серверы, PostgreSQL, Redis и worker не запускались. Тесты использовали временную SQLite БД Django, которая удалена после выполнения. Browser/E2E и production окружение этой проверкой не охвачены.

## Выполнено

Добавлен `backend/shop/test_role_action_audit.py`: 15 тестовых методов, включая матрицу GET/HEAD для 37 маршрутов действий.

| Роль | Проверенные действия и ограничения |
| --- | --- |
| admin | Создание продукта и одобрение клиента разрешены; чтение аудита разрешено; GET/HEAD бизнес-действий отклоняются |
| customer | Создание продуктов, подтверждение платежей и сдачи наличных запрещены; финансовые списки изолированы по организации; уведомления изолированы по пользователю |
| courier | Создание сдачи наличных разрешено; подтверждение платежей и сдачи запрещено; кошелек и движения изолированы даже при подстановке чужого courier_id |
| cashier | Выдача подотчетных средств и подтверждение сдачи разрешены без повторного платежа клиента; подтверждение Kaspi разрешено; сторнирование платежа и изменение продуктов/одобрения клиентов запрещены |
| accountant | Закрытие периодов, подтверждение и сторнирование Kaspi разрешены; открытие кассовой смены, выдача наличных, создание и подтверждение сдачи запрещены |

Проверяются не только HTTP-коды, но и отсутствие нежелательных изменений продуктов, состояния клиента, платежей, ledger, кассовых движений и чужих уведомлений. Отдельный тест использует настоящую Django session и `enforce_csrf_checks=True`: POST без CSRF → 403, POST с CSRF без Idempotency-Key → 422, состояние сдачи неизменно.

## Найдено и исправлено

`routes.py` обрабатывал `handovers/{id}/confirm` и `refunds/{id}/confirm` без проверки метода. Авторизованный cashier мог сделать GET без CSRF и Idempotency-Key и получить 200, состояние confirmed и денежные движения. Два регрессионных теста до изменения воспроизвели реальную мутацию. Настоящий session GET также воспроизвел проблему.

В `shop/http_methods.py` добавлен общий запрет методов, отличных от POST, для маршрутов действий. Он вызывается в начале `views.route_request`, до обработчиков и транзакций. Отказ GET → 405 METHOD_NOT_ALLOWED. HEAD уже отклоняется DRF с 405. Также GET `orders/{id}/<suffix>` больше не маскируется под чтение детализации заказа, включая неизвестный суффикс. Законные GET коллекций и чтение объектов остаются доступными.

Также исправлен GET delivery-points: клиент видел неподтвержденные точки своей организации. Новый тест воспроизвел выдачу лишней точки; добавлен `confirmed=True` в customer queryset `routes.py`. Проверено, что чужие точки недоступны даже с client_id в запросе, а admin продолжает видеть все точки.

## Остающиеся вопросы

- GET batches/quotas разрешает cashier/accountant, тогда как контракт указывает admin. Нужно согласовать права и контракт; в рамках этого изменения не изменено.
- Существующие тесты фото явно разрешают назначенному курьеру читать историю доставленных заказов и прикладывать фото возврата; контракт формулирует доступ как активное назначение. Это расхождение требований, а не доказанная в рамках аудита новая уязвимость.
- Ответ на POST чтения чужого уведомления имеет 200, хотя уведомление не меняется. Контракт общее правило чужого объекта формулирует как 404; изоляция состояния проверена, семантика кода ответа не исправлена.
- Полная матрица каждого бизнес-действия каждой роли, UI-кнопки, PostgreSQL row locks и конкурентные запросы не проверены этим набором. Workflow заказов и фоновые задачи проверяются отдельно; результат этого документа не означает полную приемку всех маршрутов MVP.
