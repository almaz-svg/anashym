# Архитектура и последовательность поставки

Источник: ТЗ «Система заказов кондитерской», версия 0.2 от 13.10.2026; прочитан исходный DOCX через ZIP/XML. Уточнения владельца в текущем обсуждении имеют приоритет. ТЗ уже одобрено для разработки; открытые эксплуатационные вопросы не блокируют срез на тестовых данных.

## Предметная модель и границы

Одна кондитерская, KZT, бизнес-часовой пояс Asia/Almaty; события хранятся в UTC, суммы NUMERIC(18,2), в JSON — строки с двумя знаками. Продажа целыми порциями. Роли: администратор, заказчик, курьер, кассир, бухгалтер. Пользователь — человек, клиент — постоянный покупатель любого типа, включая частного покупателя. Историческое имя ClientOrganization не должно ограничивать клиента юридическим лицом.

В профиле клиента обязательны категория (кофейня, магазин, ресторан/кафе, компания, частный покупатель, другое), описание деятельности и примерный объем/частота заказов. Для категории «другое» обязателен поясняющий текст. BIN необязателен. Сотрудники одного клиента имеют общие заказы и расчеты; точки доставки принадлежат клиенту. Саморегистрация создает pending-профиль без отсрочки, доступ активирует администратор. Первый срез использует заранее созданные тестовые профили со всеми обязательными полями.

Долг возникает при фактической передаче товара. Заказ резервирует склад и кредитный лимит, но не начисляет долг. Баланс = начисления − кредитовые корректировки − подтвержденные оплаты + фактические возвраты денег. Положительный баланс — долг, отрицательный — аванс. Кредитная нагрузка = max(баланс, 0) + активный кредитный резерв. Просрочка блокирует новые заказы с отсрочкой. Периоды 7/14/30 дней начинаются от одобренной даты подключения, с исключающей правой границей.

## Компоненты

React + TypeScript обращается к Django REST Framework через /api/v1 на одном origin. PostgreSQL — источник истины для прав, резервов, заказов и расчетов. Приватное файловое хранилище — фото. Django worker/management commands освобождает резервы, закрывает периоды, выполняет outbox и создает еженедельные отчеты. Redis и отдельный брокер для начального MVP не обязательны. Периодический запуск предоставляет окружение развертывания; команды идемпотентны.

Backend разделяется на accounts/clients, catalog/inventory, orders/delivery, accounting/payments, reports, audit. Сервисный слой владеет бизнес-транзакциями; serializers проверяют форму запроса, permissions и queryset ограничивают область данных. UI не рассчитывает права, остатки или финансовые итоги самостоятельно.

Сессия HttpOnly/Secure/SameSite=Lax и CSRF; HTTPS в эксплуатации. Чужой объект — 404, запрещенная операция внутри доступной области — 403. Роль нельзя менять через профиль. Административные исправления проводятся связанными операциями с причиной; финансовая история не перезаписывается. Контакты и секреты не входят в логи.

## Инварианты первого среза

- Сущности: User, Client, DeliveryPoint, Product, StockBatch, ProductionQuota, Order, OrderItem, Reservation, CreditReservation, ReceivableEntry, IdempotencyRecord, AuditEvent. Для баланса достаточно реестра начислений; будущие платежи подключаются без ручного редактирования итога.
- Цена, название, единица и адрес фиксируются в снимках заказа. Проверка expected_unit_price предшествует резервированию. В заказе 1–100 уникальных товаров, количество 1–10000.
- Создание заказа атомарно блокирует клиента, затем партии/квоты в стабильном порядке. Проверяются одобрение, просрочка, лимит, окно доставки, цена и доступность. Любой отказ откатывает весь заказ.
- Готовый склад резервируется по ближайшему сроку годности; просроченное/карантинное не продается. Предзаказ резервирует отдельную производственную квоту, с учетом cutoff.
- Idempotency-Key UUID имеет область user + method + path, хранится 7 дней. Тот же ключ и тело возвращают исходный ответ; другое тело — 409. Конкурентный повтор защищен уникальным ограничением БД.
- Для отсрочки резерв submitted истекает через 60 минут (настраиваемое значение ТЗ). Идемпотентная команда освобождает складской и кредитный резервы одной транзакцией. Проверка даты истечения также исключает продажу уже неактивного резерва.

## API первого среза (контракт 0.1)

Общий префикс /api/v1. UUID строками; snake_case; даты YYYY-MM-DD; время RFC3339. Неизвестные входные поля — 422. Списки {items, next_cursor}, limit 1–100 (20 по умолчанию), cursor непрозрачный. Ошибка: {code, message, field_errors, details, request_id}.

- GET /auth/csrf → 204 с CSRF cookie; POST /auth/login {phone E.164, password} → {user_id, role, client_id}; GET /auth/me — тот же ответ; POST /auth/logout → 204.
- GET /catalog?delivery_date=YYYY-MM-DD → список {id, name, unit:"portion", price_amount, currency:"KZT", available_qty, preorder_available_qty, preparation_minutes}. Дата от сегодня до +90 дней; требуется активный клиент.
- POST /orders с Idempotency-Key: {kind:"regular"|"preorder", delivery_point_id, requested_delivery_at, payment_mode:"deferred", items:[{product_id, quantity, expected_unit_price}]}. regular — сегодня в разрешенном окне; preorder — будущая квота до cutoff.
- POST /orders → 201; GET /orders/{id} → {id, client_id, kind, status:"submitted", payment_mode:"deferred", currency, total_amount, created_at, requested_delivery_at, reservation_expires_at, delivery_point_id, items:[{product_id, name, unit, quantity, unit_price_amount, line_total_amount}], version}.
- GET /orders → собственные заказы, стабильный порядок created_at,id. Это практическое дополнение кабинета к API-01–04; конкретная схема фиксируется в общем OpenAPI до реализации.
- GET /balance → {currency, balance_amount, debt_amount, advance_amount, overdue_amount, reserved_credit_amount, credit_limit_amount, available_credit_amount, period_days, period_start, period_end_exclusive}. debt=max(balance,0), advance=max(-balance,0), available=max(limit−debt−reserved,0).

Ошибки: 401 UNAUTHENTICATED; 403 FORBIDDEN; 404 NOT_FOUND; 409 STOCK_UNAVAILABLE, CREDIT_LIMIT_EXCEEDED, CREDIT_OVERDUE, PRICE_CHANGED, IDEMPOTENCY_CONFLICT; 422 VALIDATION_ERROR; 429 RATE_LIMITED; 503 TEMPORARILY_UNAVAILABLE. При потере ответа UI повторяет исходный ключ. Первый срез не изображает доставку или оплату локальной сменой статуса.

## Последовательность срезов

1. Контракт и основание: OpenAPI, каркасы React/Django, PostgreSQL, миграции и тестовый seed; зафиксированные зависимости и инструкция запуска.
2. Вертикальный срез: вход → каталог → корзина → заказ с отсрочкой → складской/кредитный резерв → заказ и баланс; команды истечения; проверки конкуренции и изоляции клиентов.
3. Управление клиентами и каталогом: регистрация с обязательным профилем, одобрение и лимиты, точки доставки, товары, партии/корректировки и квоты, журнал.
4. Подготовка и доставка: принятие, квота → фактическая партия, назначение курьера, выезд, фото, частичная передача/неудача и карантин. Передача атомарно заменяет кредитный резерв начислением.
5. Платежи и касса: отдельные экраны «Оплаты» (заявки и подтвержденные поступления) и «Долги» (начисления, сроки, просрочка, резерв и аванс). Kaspi подтверждает кассир/бухгалтер вручную; «Я оплатил» баланс не меняет. Наличные уменьшают долг при получении курьером, сдача в кассу — внутреннее движение без повторного погашения. Периоды и распределение оплат — часть этого среза.
6. Отчеты: автоматический еженедельный отчет оборота и ручной отчет за произвольный период; одинаковый расчет для UI/CSV. Оборот определяется по фактически переданным товарам и одобренным возвратам, поступления показываются отдельной метрикой. Сохраняются start/end_exclusive, бизнес-часовой пояс, cutoff и версия расчета. Для автоматического запуска ключ недели и типа отчета уникален, повтор не создает дубль. Базовое расписание: понедельник 00:10 за предыдущую календарную неделю, параметризуемое до пилота. Готовый отчет доступен в кабинете; отправка во внешние каналы не входит в текущий объем.
7. Возвраты/обмен: физический возврат, карантин, кредитовая корректировка, возврат денег из аванса, связанный новый заказ.
8. Пилот: полные права пяти ролей, доступность и мобильные состояния, backup/restore, нагрузка, эксплуатационные настройки и реальные данные после подготовки окружения.

## Проверки и риски

Первый срез проверяется на настоящем PostgreSQL: два заказа по 7 при остатке 10 дают один успех; при долге 30000 и лимите 50000 два заказа по 15000 не проходят оба; повтор ключа дает один заказ; PRICE_CHANGED/422 оставляют нулевые новые резервы; чужой заказ дает 404; истечение освобождает оба резерва ровно один раз. Контрольный seed: 20 порций по 1500, лимит 50000, долг 0; заказ 10 → резерв 15000, доступный лимит 35000, долг остается 0.

Без работающего PostgreSQL нельзя заявлять доказанной конкурентную безопасность; SQLite допустим только для ограниченного локального знакомства с интерфейсом. Автоплатежи Kaspi не предполагаются без договорного API. До пилота уточняются реальные окна/сроки, политика возврата пищевой продукции, хранение фото и персональных данных, кассовые документы, лимиты и хостинг. Эти решения конфигурируются отдельно от разработки одобренного первого среза. Любые demo-режимы должны быть явно обозначены и не подменять подтвержденные финансовые операции.
