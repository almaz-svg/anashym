Статус на 14.10.2026: независимые HTTP/API проверки выполнены повторно после последних исправлений на настоящем PostgreSQL 18 (`127.0.0.1:54329`), API `127.0.0.1:8000`: 23 PASS. Дополнительные проверки предзаказа/истечения: 5 PASS. Браузер Chromium, UI `127.0.0.1:5173`, ширины 360/1440: 19 PASS. Все три запуска завершились exit code 0. Полные фактические результаты: `qa/api-results.json`, `qa/expiry-quota-results.json`, `qa/ui-results.json`.

`qa/api_checks.py` выполняет HTTP-запросы с настоящими cookie и CSRF к работающему серверу. Изолированные QA-профили и товары создаются в PostgreSQL через ORM. Скрипт требует `QA_ALLOW_FIXTURES=1`, запрещает SQLite и не удаляет существующие данные. Тестовые записи помечены QA.

Покрытие: вход/сессия, анонимный доступ, CSRF, обязательная категория регистрации и пояснение «другое», pending-доступ, создание заказа, кредитный резерв без долга, изменение цены без побочных эффектов, неизвестные поля, чужие заказ и точка доставки, повтор ключа и конфликт тела. Два конкурентных HTTP-запроса стартуют через barrier; проверяются реальный итог БД и один успешный заказ при дефиците склада или кредита, отдельная гонка одного ключа.

Браузерные проверки выполнены: ширины 360/1440; вход, три товара каталога, долги отдельно от оплат; регистрация с «другое», обязательность пояснения, успешный pending-экран. На 1440 дополнительно выполнен предзаказ Медовика на завтра и показано серверное подтверждение с историей заказов. Горизонтального переполнения документа нет. Неожиданных console.error и pageerror нет; ожидаемый 401 от проверки отсутствующей сессии на странице входа исключен из ошибок. Скриншоты `qa/login-*.png`, `qa/catalog-*.png`, `qa/debt-*.png`, `qa/registration-*.png`, `qa/pending-*.png`, `qa/order-1440.png`. Каталог 1440/360 дополнительно просмотрен визуально.

Последующие функции доставки, оплаты и отчетов не считать реализованными в первом срезе.

## Фактический запуск

Команда из корня проекта (PowerShell):

```powershell
$env:DB_HOST='127.0.0.1'
$env:DB_PORT='54329'
$env:DB_PASSWORD=''
$env:QA_ALLOW_FIXTURES='1'
backend/.venv/Scripts/python.exe qa/api_checks.py
```

Подтверждены все перечисленные HTTP-сценарии. Гонка склада: при 10 порциях два запроса по 7 дали один 201 и один STOCK_UNAVAILABLE 409; DB reserve=7, один заказ. Гонка кредита: долг 30000, лимит 50000, два заказа по 15000 дали один 201 и один CREDIT_LIMIT_EXCEEDED 409; reserve=15000, один заказ. Конкурентный одинаковый ключ вернул одинаковый 201 и один order id, БД содержит один заказ.

После повторных запусков все товары с префиксом QA переведены в active=False; демонстрационный каталог содержит только три исходных товара. История QA-заказов сохранена, существующие данные не удалялись. Браузерная проверка создала реальные тестовые предзаказы demo-клиента; резерв отражается в его доступном лимите, долг остается нулевым. API оставлен работающим.

`qa/expiry_quota_checks.py` создал предзаказ 10 из квоты15: резерв квоты10, склад0. После контролируемого истечения команда освободила квоту и кредит, статус cancelled; второй запуск отменил0 заказов, не изменил резерв/версию повторно. Истекший cutoff дал STOCK_UNAVAILABLE409. Это реальные HTTP/ORM/management-command проверки на PostgreSQL.

Повтор запуска UI: `node qa/ui_checks.cjs` с bundled Node; скрипт использует bundled Playwright, поскольку bundled Python не содержит пакет Playwright. Перед финальным запуском исправлены только QA selectors и ожидание ответа каталога; промежуточные timeout относились к измененному тексту статуса/accessible label и ожиданию async-рендера.

Ограничения: контролируемые гонки двух запросов не заменяют нагрузочный тест. Заказ через UI выполнен на1440; на360 выполнены вход, каталог, долги и регистрация. Не проверены реальная доставка, оплаты, отчеты, production HTTPS, backup/restore и полный OpenAPI schema conformance. Первоначальные расхождения password8/10, HH:MM:SS/date-time и дополнительное description переданы разработчику/архитектору; итоговый контракт проверяет отдельный ревьюер. Функции будущих срезов не заявляются готовыми.
