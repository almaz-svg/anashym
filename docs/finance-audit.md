## Новые автоматические проверки

Файл: `backend/shop/test_finance_audit.py`, 6 тестов.

1. Pending Kaspi не изменяет долг; customer не может подтвердить платёж. Подтверждение cashier, повтор с тем же idempotency key и повтор с новым ключом оставляют ровно одну запись платежа.
2. Попытка подтвердить второй платёж с уже занятым Kaspi reference возвращает 409, сохраняет pending и не меняет баланс.
3. Сдача 120 из кошелька 150 резервирует средства. Подтверждение фактических 100 без причины отклоняется; с причиной оставляет 50 у курьера и 100 в кассе. Повтор отклоняется. Клиентский долг 100 и реестр не меняются.
4. Наличная доставка на 100 с получением 150 и сдачей 50 откатывается при отсутствии разменных денег: товар остаётся в резерве, нет delivery/payment. После выдачи размена 50 доставка проходит, кошелёк равен 150, платёж равен net 100; повтор не начисляет повторно.
5. Два долга по 100, первый оплачен. Возврат первого товара освобождает allocation и направляет 100 на второй долг. Второго платежа нет, return credit проводится один раз.
6. Аванс 150, pending refund 100: ledger остаётся -150, доступный аванс 50, резерв возврата 100. Новый возврат 51 отклоняется; подтверждение оставляет -50, повтор не создаёт вторую запись refund.

Общий assertion сравнивает cached client balance с суммой ledger; проверяет неотрицательность и верхнюю границу allocation по каждому payment, отсутствие allocation неподтверждённым платежам и предел allocation по заказу с учётом return credit.

## Границы результата

- В проверенных сценариях воспроизводимого финансового дефекта не обнаружено. Это не подтверждение всех требований финансового контура.
- SQLite не проверяет реальные конкурентные блокировки PostgreSQL; гонки двух подтверждений в независимых транзакциях требуют отдельного теста на целевом движке.
- Фотографии здесь представлены сохранёнными metadata fixtures; загрузка/декодирование файлов и браузерные действия не проверялись.
- Ручной внешний факт поступления Kaspi или фактического возврата денег не проверяется автоматически. Ответ API не доказывает банковский перевод.
- В контракте указан optional `original_payment_id` для создания refund, но текущий обработчик не использует его и модель Refund не хранит такую связь. Новые тесты проверяют общий аванс клиента, а не привязку возврата к исходному платежу; это ограничение соответствия контракту.
- Контракт описывает FIFO по due_at,event_at,id; код использует время первого delivery и id. Новый модуль не проверяет случай разного порядка due_at после изменения периода расчётов.
- Исправление отмены failed delivery после физической сдачи и GET mutation guards ведутся отдельно и здесь не дублируются.
