# Локальный запуск и эксплуатационная проверка

Решение владельца от 14.10.2026: сначала полностью рабочая локальная версия. Публикация отложена; здесь используются демонстрационные данные и ручное подтверждение Kaspi.

## Постоянный запуск

Задача Windows `ConfectioneryLocal` запускается при входе пользователя Windows и выполняет `scripts/run-local.ps1`. Она управляет PostgreSQL на 127.0.0.1:54329, Waitress на 127.0.0.1:8000, Vite на 127.0.0.1:5173 и одним worker. Запуск скрытый; открытое окно терминала не требуется. Приложение: http://localhost:5173.

- `scripts/install-local-task.ps1` устанавливает/запускает задачу и проверяет принадлежность workspace.
- `scripts/restart-local-task.ps1` проверяет путь задачи, завершает только процессы этого проекта и их потомков, корректно останавливает его кластер и запускает задачу заново. Это требуется после изменения Python-кода.
- `logs/local-processes.json` содержит время запуска и PID процессов. Логи API, интерфейса, worker и PostgreSQL находятся в `logs/`.

Supervisor проверяет PostgreSQL и дочерние процессы каждые 30 секунд. Если база остановилась, он запускает тот же кластер. При старте не создаёт второй worker и не занимает порт чужого приложения. В первоначальном варианте остановка задачи оставляла прежний API работающим; скрипт исправлен явным завершением проверенных процессов. Повторный seed сохраняет изменённые пароли и роли существующих сотрудников.

PostgreSQL использует trust только на loopback. Настройки предназначены для данного локального тестового окружения. Waitress использует 4 потока, постоянные соединения Django с БД до 60 секунд и проверку их состояния. Таймаут подключения к БД — 5 секунд.

`GET /live` проверяет процесс; `GET /ready` — БД и отсутствие неприменённых миграций. При недоступной БД readiness возвращает 503. Одна успешная readiness-проверка не заменяет финансовую приёмку.

Ручной запуск: `start-backend.ps1`, `npm run dev` из frontend, `start-worker.ps1`. Пока задача Windows работает, второй комплект процессов не запускайте. Compose проверен синтаксически; Docker daemon здесь не работал, контейнерный запуск не заявляется проверенным.

## Автоматические операции и копии

Worker каждые 30 секунд освобождает истёкшие резервы, закрывает завершённые расчётные периоды, сохраняет недельные отчёты и проверяет ежедневную резервную копию. Компьютер должен быть включён. Повторы не дублируют проводки и снимки.

Автоматическая генерация догоняет пропущенные завершённые недели с первой записи реестра. Готовый архив не пересчитывается. Явный CLI `generate_weekly_reports --start YYYY-MM-DD` создаёт снимок указанной недели на момент вызова, даже если неделя ещё не закончилась; для текущего оперативного отчёта используйте раздел «Отчёты».

`scripts/daily_backup.py` создаёт `backups/daily-YYYY-MM-DD.zip` по дате Asia/Almaty один раз в день. `scripts/backup.py --output backups/<name>.zip` создаёт дополнительную копию: PostgreSQL custom dump, приватные фотографии, SHA-256 manifest. Архив публикуется атомарно после записи; существующая копия не перезаписывается. DB_* задаёт подключение, пароль в архив/вывод не включается.

`backend/.venv/Scripts/python.exe scripts/verify_restore.py backups/<name>.zip` создаёт новую БД verify_<id>, восстанавливает dump, проверяет хеши файлов, наличие всех фото по ссылкам БД и равенство каждого cached balance сумме его реестра. Основная база не перезаписывается. Проверочная БД и каталог restore-checks остаются для осмотра.

Проверка `backups/local-20261014-final.zip` от 14.10.2026: восстановлены 61 заказ, 56 записей реестра с суммой 64 795.00 KZT; проверены 84 файла, найдены все 36 ссылок на фото. Расхождений балансов с реестром — 0. Восстановление заняло 0.953 секунды; результат: `restore-checks/verify_8df4b15f2cf74ae5/result.json`. Это размер набора в тот момент, не RTO будущего производственного объёма. Позднейшая проверка фиксируется отдельно ниже.

## Нагрузка и граница результата

После последних изменений сделана дополнительная копия `backups/local-20261014-release.zip`: 76 заказов, 60 проводок на 63 195.00 KZT, 90 проверенных файлов, расхождений балансов 0. Восстановление в `verify_1de952eea9b24afd` прошло за 1.453 секунды. Результат сохранён в `restore-checks/verify_1de952eea9b24afd/result.json`. Основная база продолжала работать.

`qa/benchmark_fixture.py` создал в отдельной восстановленной БД verify_c606cee1d3d64881 100 000 синтетических заказов и 500 000 строк. Вместе с исходными данными там 100 018 заказов и 500 018 строк. Основная база эти записи не содержит.

`qa/load_read.py` открывает 50 авторизованных сессий до измерения. Каждая сессия раз в секунду читает уведомления и чередует заказы, каталог, баланс. Транспорт — HTTP keep-alive. Секреты сессий в результат не записываются. Все значения ниже получены на общем Windows-ноутбуке разработки; ограничение до 2 vCPU/4 GB не применялось.

| 32 потока, одновременный старт | 1000 | 0 | 1797 | qa/benchmark-browser-transport-results.json |

Цель обычного чтения p95 < 500 мс достигнута в равномерном сценарии, но не при синхронном всплеске. Среднее в равномерном сценарии — 104.448 мс. Предыдущие результаты с закрытием TCP после каждого запроса и прерванные запуски сохранены как диагностика; они не заменяют эти измерения.

Каталог получает доступность партий и квот одним запросом; страницы заказов используют ограниченную выборку, доступный аванс вычисляется один раз на клиента страницы. Регрессионные тесты проверяют суммы и ограниченное число запросов. Количество потоков выбрано по измерениям.

QA измерил появление одного нового уведомления в открытом браузере за 925 мс. Это один пример, не p95. Массовое создание заказов с целью p95 < 1 секунды и распространение событий под полной нагрузкой отдельно не измерены. Конкурентные проверки остатков, лимита и кассовой сдачи на PostgreSQL описаны в mvp-qa.md.

## Граница запуска для реальных клиентов

Локальные проверки операций, ролей, приватных фото и сборки описаны в mvp-qa.md и mvp-review.md. Реальные реквизиты Kaspi, HTTPS, production-секреты, второй фактор администратора, политика хранения и хостинг не настроены. Внешнее автоматическое подтверждение Kaspi не входит в этот MVP. Машиночитаемый openapi.yaml описывает первый срез; полный текущий API описан в mvp-contract.md, его полная схема ещё требует синхронизации.
