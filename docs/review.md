# Независимое ревью первого среза

Дата: 14.10.2026. Проверены production-файлы backend/config, backend/shop (модели, обработчики, admin, миграции, seed и expiry), frontend/src, Compose, Dockerfile и start-backend.ps1. Основание: source-tz.txt, architecture.md, openapi.yaml и план первого среза. Применён requesting-code-review/SKILL.md. Код ревьюер не изменял.

## Найденные ошибки и повторная проверка

1. **P1 — потеря резервов при сохранении клиента администратором. Исправлено.** `readonly_fields` запрещал ввод, но обычный `obj.save()` записывал старое значение reserved_credit. На настоящем PostgreSQL воспроизведено: ORM-объект загружен с 0; отдельный UPDATE устанавливает 1500; ClientAdmin.save_model со старым объектом возвращает значение к 0. После исправления тот же сценарий сохраняет 1500. Проверка выполнялась внутри transaction.atomic с rollback. Admin теперь блокирует клиента и перечитывает финансовые значения перед сохранением. Для существующих Batch/Quota изменение запрещено: это исключает аналогичную потерю складского резерва; новые записи добавлять можно.

2. **P1 — два написания одного UUID обходили запрет повторного товара. Исправлено.** UUID с дефисами и UUID.hex считались разными строками. Две загрузки партии давали независимые объекты с одинаковым reserved; последовательные save могли записать 7 вместо 14 при двух Reservation по 7. Истечение затем не могло корректно освободить резерв. После канонизации uuid.UUID повторная проверка на PostgreSQL отклоняет второй alias с VALIDATION_ERROR/422 до резервирования. Добавлен regression test.

3. **P1 — неопределённый HTTP 5xx сбрасывал ключ заказа. Исправлено по коду.** После возможного commit и ошибки ответа повтор создавал новый ключ и второй заказ. UI теперь сбрасывает попытку только при определённом HTTP 4xx; сетевые сбои и 5xx сохраняют исходный ключ и тело при неизменённой корзине. Браузерный сбой после реального commit ревьюером не инжектировался.

4. **P1 — period_days=0 вызывал бесконечный цикл /balance. Исправлено.** PositiveIntegerField допускал ноль через admin, цикл прибавлял ноль. Теперь choices и DB CHECK допускают только 7/14/30. Прямая попытка UPDATE period_days=0 на PostgreSQL подтверждённо отклонена IntegrityError.

5. **P2 — ответы каталога для старой даты перезаписывали новую дату. Исправлено по коду.** В load введён номер поколения: результаты, ошибки и finally старого запроса не меняют актуальное состояние.

6. **P2 — регистрация принимала размеры сверх PostgreSQL-полей. Исправлено по коду.** Ранее name/frequency до 1000 попадали в varchar(200), category_other и quantity не имели соответствующих границ: вместо 422 возникал DataError/500. Теперь name/frequency/category_other ограничены 200, description 1000, quantity 1..1000000. В тесты добавлена проверка сверхдлинного имени.

7. **P2 — составной throttle IP+phone не ограничивал аккаунт и IP независимо. Исправлено по коду.** Теперь отдельные hash-счётчики телефона и IP блокируются в стабильном порядке; смена одного компонента не создаёт обход другого. Проверка независимых лимитов в HTTP-нагрузке не проводилась ревьюером.

## Дополнительные замечания и повторное чтение

- **P2, frontend, исправлено по коду:** после выхода сохранялись orders/products/points и выбранный point; вход другого клиента мог кратко показать данные прошлого клиента и оставить чужую точку выбранной. logout теперь очищает все эти значения, корзину, attempt/cache и инвалидирует loadVersion.
- **P2, frontend, исправлено по коду:** после выбора товара со второй страницы «Обновить» заменял products первой страницей, сохраняя qty. submit брал строки только из products, поэтому выбранная скрытая позиция исчезала из отправляемого заказа. Теперь отдельный catalogCache сохраняет метаданные загруженных товаров; submit строит строки по нему и qty независимо от видимой страницы.
- **P2, backend, исправлено по коду:** конкурентная регистрация одного телефона проходила exists() в обоих запросах; unique username мог вернуть необработанный IntegrityError/500. endpoint теперь перехватывает IntegrityError регистрации после выхода из откатываемой atomic-транзакции и возвращает VALIDATION_ERROR/422; клиент, созданный неуспешной транзакцией, откатывается.

Повторное чтение всех трёх изменений выполнено. Независимый запуск frontend npm test после изменений: 3 PASS, exit code 0 (20:45:42). Эти unit tests проверяют API-границу и классификацию неопределённой ошибки 502, но не заменяют браузерные тесты пагинации и смены клиента. Открытых P1/P2 в проверенном коде первого среза после этих исправлений не осталось; это ограниченный вывод ревью, а не доказательство отсутствия любых дефектов.

## Границы заключения

Основной заказ резервирует товар и лимит одной транзакцией; начисление долга при создании отсутствует. Чужие объекты ограничены клиентом, анонимный вход защищён CSRF; ранее проведённые независимые 23 HTTP-проверки PostgreSQL отражены в qa.md. Ревьюер дополнительно проверил описанные выше DB-инварианты, но не повторял весь набор QA и не проводил нагрузочное тестирование.

Оплаты, доставка, начисления при передаче, возвраты, отчёты и полная эксплуатационная защита не входят в принятый первый срез. Их отсутствие не является дефектом этого среза; интерфейс сообщает об отсутствии платежей и экспорта. Compose содержит worker истечения каждые 30 секунд. Локальный start-backend.ps1 запускает API, а start-worker.ps1 — отдельный цикл истечения каждые 30 секунд; README требует третий терминал для worker. Скрипт прочитан ревьюером; бесконечный цикл им не запускался.

Контракт повторно сверен: User соответствует me(), DeliveryPoint использует строку HH:MM:SS, Product допускает description; границы RegisterInput теперь совпадают с проверками размеров в backend. Ответы допускают дополнительные поля согласно исходному API-01.

Демонстрационные аккаунты и DEBUG допустимы только в описанном локальном тестовом окружении. Документ не подтверждает готовность к реальным взаиморасчётам или production.
