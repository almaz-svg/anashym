# Anashym — система заказов для кондитерской

Веб-приложение для кондитерской и её постоянных покупателей: от выбора десертов и оформления заказа до доставки, оплаты и сверки задолженности. Клиенты, администраторы, курьеры, кассиры и бухгалтеры работают в одной системе с доступом по ролям.

Интерфейс доступен на казахском, русском и английском языках, поддерживает светлую и тёмную темы. Расчёты ведутся в тенге (KZT), бизнес-часовой пояс — `Asia/Almaty`.

[Открыть приложение](https://anashym-kappa.vercel.app) · [Документация](#документация) · [Локальный запуск](#локальный-запуск)

## Что умеет приложение

- **Каталог и заказы.** Товары, цены, готовые партии, производственные квоты, корзина и предзаказы. При оформлении сервер проверяет доступность и резервирует товар.
- **Кабинет клиента.** Профиль, адреса доставки, история заказов, условия отсрочки, задолженность, аванс и платежи, ожидающие подтверждения.
- **Регистрация и доступ.** Заявки покупателей с одобрением администратора, приглашения сотрудников и разграничение прав.
- **Доставка.** Подготовка заказа, назначение курьера, выезд, полная или частичная передача с приватной фотографией, обработка неудачной доставки.
- **Оплаты и касса.** Наличные, заявки на оплату через Kaspi, отсрочка, частичные оплаты, авансы, учёт денег у курьера и передача кассиру.
- **Возвраты.** Приём товара, карантин, списание, корректировка расчётов, возврат средств и обмен через связанный новый заказ.
- **Финансовый учёт.** Реестр начислений и оплат, расчётные периоды 7/14/30 дней, просрочка, отчёты за выбранный период и выгрузка CSV.
- **Контроль операций.** Уведомления, журнал действий, фоновые задачи и проверка доступа к фотографиям.

Заказ сам по себе не создаёт долг. Заявка Kaspi уменьшает задолженность только после ручного подтверждения, а передача наличных от курьера кассиру не учитывается как повторная оплата клиента.

## ИИ-помощник для повторных заказов

В проекте представлен демо-сценарий ИИ-помощника для постоянных покупателей. Его задача — упростить регулярные покупки: предложить клиенту привычный заказ, сохранив состав товаров и их количество.

Например, кофейня каждую неделю заказывает 10 медовиков и 5 чизкейков. Помощник предлагает повторить этот набор без изменений, чтобы покупателю не приходилось заново собирать корзину. Перед оформлением клиент проверяет и подтверждает заказ, а система проверяет актуальные цены и наличие товаров.

Сценарий демонстрирует идею функции; подключение ИИ к истории покупок и автоматическое формирование предложения пока не реализованы.

## Роли

- **Клиент** — оформляет заказы, выбирает адрес и способ оплаты, следит за доставкой и взаиморасчётами.
- **Администратор** — одобряет покупателей, управляет каталогом, заказами, доставкой и доступом сотрудников; может оформить заказ от имени клиента.
- **Курьер** — работает с назначенными доставками, фиксирует передачу товара и полученные наличные.
- **Кассир** — принимает деньги от курьеров и работает с кассовыми операциями.
- **Бухгалтер** — работает с расчётами, задолженностью, периодами и отчётами.

## Технологии

- **Frontend:** React 19, TypeScript, Vite 7, Lucide React.
- **Backend:** Python 3.12, Django 5.2, Django REST Framework, Waitress.
- **База данных:** PostgreSQL; в Docker используется PostgreSQL 16.
- **Облачное хранение:** Supabase PostgreSQL и приватное хранилище фотографий.
- **Развёртывание:** Vercel Services; для локальной среды предусмотрен Docker Compose.
- **Проверки:** Django Test Runner, Vitest и Testing Library.

Браузер обращается к Django API через тот же домен. В режиме разработки Vite проксирует `/api` и `/admin` на backend. Авторизация использует серверные сессии и CSRF-защиту.

## Локальный запуск

### Вариант 1. Docker Compose

Нужны Git и запущенный Docker Desktop с поддержкой Docker Compose. Команды выполняются из корня репозитория.

1. Создайте файл окружения:

   ```powershell
   Copy-Item .env.example .env
   ```

2. В `.env` задайте собственные значения:

   ```dotenv
   DB_PASSWORD=your-local-database-password
   DJANGO_SECRET_KEY=your-long-random-secret
   ```

3. Соберите и запустите сервисы:

   ```powershell
   docker compose up --build
   ```

Compose запускает PostgreSQL, backend, frontend и worker. Backend применяет миграции и создаёт демонстрационные данные командой `seed_demo`.

- Приложение: [localhost:5173](http://localhost:5173).
- Проверка процесса API: [localhost:8000/live](http://localhost:8000/live).
- Проверка базы и миграций: [localhost:8000/ready](http://localhost:8000/ready).

Остановка:

```powershell
docker compose down
```

Данные PostgreSQL и фотографии сохраняются в отдельных Docker volumes. Текущий Compose предназначен для разработки: включён debug-режим, используются демонстрационные данные. Полный запуск контейнеров в рамках обновления README не проверялся.

### Вариант 2. Вручную на Windows

Нужны Python 3.12, Node.js 22.14+ и доступный PostgreSQL. До запуска создайте базу `confectionery` и пользователя `confectionery` с правами на неё. Скрипты ниже подключаются к PostgreSQL, но не устанавливают и не запускают его.

Подготовьте зависимости из корня репозитория:

```powershell
py -3.12 -m venv backend/.venv
./backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
Set-Location frontend
npm ci
Set-Location ..
```

В первом терминале задайте параметры локальной среды и запустите backend:

```powershell
$env:DB_PASSWORD = 'your-local-database-password'
$env:DJANGO_SECRET_KEY = 'your-long-random-secret'
./start-backend.ps1 -DatabasePort 5432
```

Скрипт применяет миграции, создаёт демонстрационные данные и запускает API на `127.0.0.1:8000`. Если не передавать `-DatabasePort`, используется порт `54329`.

Во втором терминале запустите frontend:

```powershell
Set-Location frontend
npm run dev
```

В третьем терминале из корня проекта запустите фоновые задачи с теми же параметрами базы:

```powershell
$env:DB_PASSWORD = 'your-local-database-password'
$env:DJANGO_SECRET_KEY = 'your-long-random-secret'
./start-worker.ps1 -DatabasePort 5432
```

Worker каждые 30 секунд обрабатывает истёкшие резервы, закрывает расчётные периоды, отправляет напоминания о просрочке, формирует недельные отчёты и проверяет ежедневную резервную копию. Для локальных копий требуются доступные утилиты PostgreSQL; подробности — в [инструкции эксплуатации](docs/local-operations.md).

PowerShell-скрипты получают настройки из окружения процесса; файл `.env` из варианта Docker автоматически не читается. Не запускайте второй комплект сервисов на уже занятых портах.

## Демонстрационные аккаунты

После `seed_demo` доступны:

- Клиент: `+77010000001` / `DemoClient2026!`.
- Администратор: `+77010000002` / `DemoAdmin2026!`.
- Курьер: `+77010000003` / `DemoStaff2026!`.
- Кассир: `+77010000004` / `DemoStaff2026!`.
- Бухгалтер: `+77010000005` / `DemoStaff2026!`.

Это публичные тестовые учётные записи. Используйте их только в демонстрационной среде. Повторный seed сохраняет пароли существующих пользователей.

Для знакомства с системой войдите как клиент, оформите заказ, затем откройте кабинет администратора для обработки заказа и назначения курьера. Передачу товара и наличных можно проверить под ролью курьера, приём денег — под ролью кассира.

## Проверки

Frontend:

```powershell
Set-Location frontend
npm test
npm run build
```

Backend — из каталога `backend` с настроенными `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` и `DB_PASSWORD`:

```powershell
./.venv/Scripts/python.exe manage.py check
./.venv/Scripts/python.exe manage.py makemigrations --check --dry-run
./.venv/Scripts/python.exe manage.py test shop --noinput
```

Для серверных тестов нужна отдельная тестовая БД; пользователь PostgreSQL должен иметь право её создавать. Результаты прошлых прогонов и их ограничения приведены в [QA-документации](docs/mvp-qa.md). Обновление README не означает новый прогон тестов приложения.

## Облачное развёртывание

В репозитории предусмотрена конфигурация **Vercel Services + Supabase**. Корень проекта Vercel — корень репозитория; frontend и Django работают на одном домене. Сборка backend вызывает `bootstrap_cloud` для применения миграций в схеме `bakery` и проверки приватного хранилища.

Основные серверные переменные:

- `DJANGO_SECRET_KEY` — случайный секрет Django длиной не менее 50 символов.
- `DATABASE_URL` или `POSTGRES_URL` — подключение к PostgreSQL.
- `SUPABASE_URL` — адрес проекта Supabase.
- `SUPABASE_SERVICE_ROLE_KEY` или `SUPABASE_SECRET_KEY` — серверный ключ хранилища.
- `CLOUD_JOB_SECRET` — отдельный секрет для защищённого запуска фоновых задач.

Демонстрационные данные в облаке создаются только при явном `CLOUD_SEED_DEMO=1`. Секреты должны храниться в настройках окружения хостинга и не попадать в Git или frontend-сборку.

Постоянный worker в Vercel не запускается. Для периодических операций предусмотрен защищённый `POST /api/internal/jobs`, вызываемый расписанием Supabase. Настройка описана в [документации фоновых задач](docs/background-jobs.md), требования к эксплуатации — в [production operations](docs/production-operations.md).

Локальная задача Windows `ConfectioneryLocal` отключена по решению владельца. Для облачного развёртывания её включать не требуется.

## Ограничения текущей версии

- Kaspi обрабатывается через заявку и ручное подтверждение. Интеграция с банковским API и автоматическое списание не реализованы.
- Разбор заказа из сообщения с помощью ИИ отключён до подключения провайдера. Ручное оформление администратором доступно.
- Второй фактор и реальные реквизиты продавца требуют отдельной настройки перед использованием с реальными покупателями.
- Настроенное расписание фоновых задач не подтверждает наличие проверенных облачных резервных копий. Облачное восстановление требует отдельной проверки.
- Часть эксплуатационных документов описывает исторические локальные проверки; их результаты относятся к указанным в них датам и наборам данных.
