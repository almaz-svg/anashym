# Кондитерская

Веб-сервис заказов постоянных покупателей, доставки и взаиморасчётов. React/TypeScript, Django/DRF, PostgreSQL. Қазақша, русский и English; светлая и тёмная темы; KZT, бизнес-часовой пояс Asia/Almaty.

## Открыть

[Кабинет](https://anashym-kappa.vercel.app) · [Готовность API](https://anashym-kappa.vercel.app/ready)

Рабочая версия размещается в Vercel Services: frontend и Django используют один домен, PostgreSQL и приватные фотографии хранятся в Supabase. Ноутбук владельца не используется как сервер. Задача Windows **ConfectioneryLocal** остановлена и отключена по его запросу; не включайте её и не запускайте постоянные локальные сервисы без отдельного запроса владельца.

Для публикации корнем проекта Vercel должен быть корень репозитория, framework — Services. `vercel.json` направляет `/api/*` в Django. Сборка backend запускает `bootstrap_cloud`: применяет миграции в отдельной схеме `bakery`, создаёт демонстрационные аккаунты без сброса существующих паролей и проверяет приватное хранилище. Обязательные серверные переменные: `DJANGO_SECRET_KEY`, `POSTGRES_URL` (или `DATABASE_URL`), `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (или `SUPABASE_SECRET_KEY`). Секреты не помещаются в Git или браузерную сборку.

Постоянный worker в Vercel не запускается. Автоматические резервы, уведомления, закрытие периодов и недельные отчёты требуют отдельного облачного расписания; локальная задача для этого не используется.

## Рабочие сценарии

- Профиль заказчика с личными данными, условиями отсрочки и расчётами за выбранный период. Общая задолженность, аванс и ожидающие подтверждения платежи показаны отдельно; положительный долг выделен красным. Выход, тема и язык доступны в шапке; настройки темы и языка сохраняются в браузере. Подробности: [профиль и настройки](docs/customer-account.md).
- Регистрация с категорией, описанием деятельности, ожидаемыми объёмом/частотой и предпочтительной оплатой. Доступ и отсрочку одобряет администратор. Сотрудник устанавливает пароль по одноразовому приглашению.
- Каталог, готовые партии и производственные квоты; заказ за наличные, Kaspi или с отсрочкой. Сервер резервирует товар и лимит; заказ сам по себе не создаёт долг.
- Подготовка, назначение курьера, выезд, передача с приватным фото, частичная передача, неудачная доставка и отдельная сдача непереданного товара в карантин. Предзаказ обеспечивается фактическими партиями; перенос подтверждает клиент.
- Отдельные оплаты и задолженность. Kaspi-заявка не уменьшает долг до ручного подтверждения. Наличные числятся у курьера; сдача кассиру повторно долг не уменьшает. Подотчёт, смены, расхождения, частичные оплаты и авансы учитываются отдельно.
- Реестр начислений, периоды 7/14/30 дней, просрочка, распределение оплат. Закрытые снимки не переписываются поздними операциями.
- Возвраты, физический приём, кредитовая корректировка, карантин/списание/пригодность, возврат денег из аванса и связанный новый заказ при обмене.
- Оборот, поступления, задолженность и авансы показаны отдельно. Отчёт доступен за произвольный период и в CSV. Worker сохраняет недельные снимки и закрывает завершённые периоды.
- Уведомления, журнал действий и приватные фотографии с проверкой роли при каждом доступе и ссылкой максимум на 5 минут.

## Запуск вручную и Docker

Если задача Windows работает, не запускайте вторые процессы на тех же портах. Для ручного запуска нужны Node.js, PostgreSQL и Python virtualenv `backend/.venv` с `backend/requirements.txt`. Запустите `start-backend.ps1` из корня; в другом терминале — `npm ci` и `npm run dev` из frontend; в третьем — `start-worker.ps1` из корня.

Worker должен оставаться включённым для автоматических резервов, периодов и недельных отчётов.

Для Docker Desktop скопируйте `.env.example` в `.env`, задайте свои DB_PASSWORD и DJANGO_SECRET_KEY, затем выполните `docker compose up --build`. Compose проверен синтаксически; полный контейнерный запуск здесь не проверен: Docker daemon не запущен. PostgreSQL и приватное media-хранилище имеют отдельные volumes.

## Проверки и эксплуатация

Доказательства и ограничения: [QA](docs/mvp-qa.md), [ревью](docs/mvp-review.md), [backup/restore и нагрузка](docs/local-operations.md). Спецификация: [MVP contract](docs/mvp-contract.md), [план](docs/mvp-plan.md), [исходное ТЗ](docs/source-tz.txt).

Из backend с настроенными DB_*: `.venv/Scripts/python.exe manage.py test shop --noinput`, `manage.py check`, `manage.py makemigrations --check --dry-run`. Из frontend: `npm test`, `npm run build`.

Backup: `backend/.venv/Scripts/python.exe scripts/backup.py`. Проверочное восстановление в новую изолированную БД: `backend/.venv/Scripts/python.exe scripts/verify_restore.py backups/<archive>.zip`. Существующая БД приложения не перезаписывается.

Облачная версия использует HTTPS и серверный секрет Django. В облако не переносятся локальные клиентские данные; первоначально создаются демонстрационные аккаунты. Второй фактор и реальные реквизиты продавца не настроены. Реального Kaspi API или автоматического списания нет: MVP предусматривает ручную сверку. Результаты тестов относятся к явно описанным наборам, а не к реальным продажам.
